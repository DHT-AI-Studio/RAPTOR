# Changelog

## v0.5.0 (2026-11-25)

### Known Limitations

Accepted limitations for this release. "fixed in a later release" items will move to that release's own section when resolved.

- **MCP (Module 27) stdio transport uses one shared identity for every caller.** The HTTP transport propagates each caller's own JWT; the stdio transport (`MCP_TRANSPORT=stdio`) never sets it, so every tool call made through a stdio-launched process resolves through the shared service account instead of a per-user token. Two different users each running the stdio entrypoint against the same deployment are indistinguishable to every downstream API call. (A second gap this same issue originally reported -- the agent's `client_secret` stored in plaintext in Redis -- has since been fixed: it's now stored Fernet-encrypted.)

- **NVENC hardware video encoding has a confirmed driver-level bug on multi-GPU hosts** (reproduced on a multi-GPU test host, driver 595.x): `h264_nvenc` fails deterministically on GPU 0 while working cleanly on GPU 1, independent of CUDA compute. A workaround (pin `VIDEO_CHUNKING_GPU` to a working GPU index) is shipped and confirmed effective end-to-end. The underlying NVIDIA driver bug itself is not fixed, so the same symptom could recur on a different multi-GPU host, or if GPU assignment changes, until NVIDIA ships a driver fix.

- **Media pipeline dead-letter queues (modules 09-12, ~21 topics) have no consumer, no monitoring, and no retry mechanism.** A message that lands on any `*-dlq` topic today is written once, read by nobody, and ages out silently. Module 25's own `personal-index-requests-dlq` is a separate, newer system with real alerting and is not affected.

- **gRPC gateway (Module 36): `GetAsset`, `Chat`, `GetJobStatus`, and `StreamVideo` RPCs are permanently `UNIMPLEMENTED`** for this release (each has a current replacement: `DownloadAsset`, no replacement yet, `GetJob`/`WatchJob`, and `StreamVideoSegment` respectively). Additionally: `StreamVideoSegment` only supports its `asset` source (`video_id` returns `UNIMPLEMENTED`); `JobSession` only supports the subscribe direction (cancel/control are recorded but not acted on); `AnalyzeStream` is disabled by default (`GRPC_GATEWAY_ANALYZE_STREAM_ENABLED=false`) and, even enabled, never returns analysis events back to the caller.

- **Guardrail policy enforcement screens 5 of this platform's 6 registered entry points** (`GET /guardrail/coverage/integration` on module 23 lists all six and whether each is actually wired in). Module 18 (query-orchestrator)'s MCP tool-call check has never been implemented -- no screening logic exists in that module at all, confirmed by inspecting its source; module 15 (chat-service)'s proxy already worked correctly. The other four were found broken despite each reporting itself as integrated, and fixed:
  - Modules 07 and 13's own enable switches (`AIML_GUARDRAIL_ENABLED`, `GR_ENABLED`) defaulted to `false`; now default to `true`. Confirmed live against a real deployment: a clearly unsafe prompt now correctly blocks through both.
  - Module 36's enable switch (`GRPC_GATEWAY_GUARDRAIL_ENABLED`) also defaulted to `false`, and its `GuardrailInterceptor` separately had its own timeout (`GRPC_GATEWAY_GUARDRAIL_TIMEOUT_MS`) set to 2000ms against a real decide-call latency that measured consistently ~2.7-6.6s on that same deployment -- always just over budget, so every call failed open regardless of content even once the switch was corrected. Both fixed (switch default + timeout bumped to 20000ms, matching every other module's equivalent); confirmed live: the same unsafe prompt now aborts the RPC with `PERMISSION_DENIED`.
  - Module 21 (agent-protocol)'s A2A pre-check registered itself as integrated at startup, but its text-extraction logic only recognized a standard A2A `message.parts[]` shape, which neither `agent.query` nor `agent.delegate`'s real request params ever have -- so it screened nothing for either real method, confirmed live before the fix. Fixed, with regression tests. Its own guardrail HTTP call had the same timeout problem as module 36's, independently: a hardcoded 5.0s against a real decide latency that measured ~6.5s steady-state and 15.6s on a cold start, so even after the shape fix every call still failed open. Bumped to 30.0s. Confirmed live: `agent.query` and `agent.delegate` with unsafe content now correctly return a JSON-RPC `-32600` policy violation instead of passing through; a safe control query still routes normally.

  A module's own self-reported "integrated" status in the coverage endpoint is not sufficient evidence on its own that it works -- it reflects whether a registration call was made, not whether the screening logic it describes actually runs or works.

- **Tenancy model: `branch_id` is always the caller's JWT `sub` claim** — one Keycloak account maps to exactly one per-user database/branch (`user_<sub>`), with no multi-user workspace or shared-tenant model. This is the confirmed, intended v0.5 design (see the v0.4→v0.5 migration tooling's own verification of this mapping), not an interim gap, but it constrains what access-control models this release can support.

- **Module 16 (training-service) does not build or run on ARM64** (GX10/GB10 hosts) — its Dockerfile is still pinned to `pytorch/pytorch:2.6.0-cuda12.4-cudnn9-devel`, an amd64-only base image, from the original GX10 porting pass; no fix has shipped yet. Every other currently-deployable module is confirmed to build and run on both amd64 and arm64. Modules 17/19/20 (hybrid-search, graph-database, graph-service — all deprecated in favor of Module 25) have not been specifically verified on arm64 either way, since nothing currently exercises them on that architecture.
